How an online store stays up during a DDoS attack

ShopNest is a made-up online retail store. Traffic comes in from the internet at the top and passes through six layers before it reaches the servers. Click a layer to see what it stops.

1,000,000 attack requests/sec vs. 2,000 real customer requests/sec (example numbers)

The internet: customers and a botnet of infected devices

↓

Cloud (stops attacks before they reach your network)

1. CDN and DDoS scrubbing service

Attack requests reaching this layer: 1,000,000/sec

Where it sits: In front of everything, on the provider's global network.

What it stops: Volumetric floods (UDP floods, DNS and NTP amplification) that try to fill the store's internet connection.

How it works: Traffic is spread across many data centers, and scrubbing centers drop junk traffic and forward the clean rest. The CDN also serves cached product pages, so the store's servers see fewer requests.

Example tools: Cloudflare, Akamai, AWS Shield

↓

Your network (the store's data center)

2. Edge firewall

Attack requests reaching this layer: 50,000/sec

Where it sits: At the front door of the data center, before the load balancer.

What it stops: Traffic on unused ports, spoofed source addresses, and SYN floods.

How it works: Only web ports (80 and 443) are allowed in. Ingress filtering drops packets with impossible source addresses, and SYN cookies keep half-open connections from filling the connection table.

Example tools: Palo Alto, Fortinet, Cisco ASA, iptables

↓

3. Intrusion prevention system (IPS) and rate limiter

Attack requests reaching this layer: 20,000/sec

Where it sits: Directly behind the firewall, inspecting what it lets through.

What it stops: Known attack patterns, and single sources sending far more requests than a person would.

How it works: The IPS matches traffic against attack signatures and blocks it automatically. The rate limiter caps requests per IP address and temporarily bans sources that go over.

Example tools: Snort, Suricata, Cisco Firepower, NGINX rate limiting

↓

4. Web application firewall (WAF) and load balancer

Attack requests reaching this layer: 5,000/sec

Where it sits: Just in front of the web servers.

What it stops: HTTP floods that look like real shoppers, such as repeated searches and checkout requests.

How it works: The WAF reads the web requests and challenges suspicious clients with a CAPTCHA or browser check. The load balancer spreads the remaining traffic evenly and avoids servers that are struggling.

Example tools: AWS WAF, ModSecurity, F5 BIG-IP, HAProxy

↓

5. Web and application servers

Attack requests reaching this layer: 1,000/sec

Where it sits: Behind the load balancer, in an autoscaling group.

What it stops: Whatever slips through. The goal here is to keep serving customers instead of crashing.

How it works: Servers scale out automatically when load rises. If they are still stressed, the store serves cached pages, queues checkout, and turns off non-essential features.

Example tools: Autoscaling groups, Redis or Memcached caches, message queues

↓

6. Database

Attack requests reaching this layer: 100/sec

Where it sits: On a private network, reachable only from the application servers.

What it stops: Direct attacks. The database has no public address, so attackers cannot aim at it.

How it works: A cache answers most repeat reads, and read replicas share the rest, so orders and payment records stay safe while the front of the store is under pressure.

Example tools: Private subnets, read replicas, connection pooling

Request counts are made up to show the idea. Each layer catches what the one before it missed, so no single failure takes the store down.
